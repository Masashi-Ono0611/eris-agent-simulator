## 2. P差の測定分解

### 2.1 足し上げ可能な会計式

成功したWETH/WBTC現物約定tについて、買いを符号s=+1、売りをs=−1、実数量q、実価格p、包含ブロックの参照価格f、最終ブロックの参照価格Fとする [A,B,M]。

```text
E_exec = Σ s*q*(f-p)          約定時点の参照価格に対する差額
M_carry = Σ s*q*(F-f)         約定後から最終評価までの価格変動分
G = Σ gasUsed*min(tip,cap)/1e18 * F_WETH
X = (P-P_noop) - E_exec - M_carry + G
ΔP = ΔE_exec + ΔM_carry - ΔG + ΔX       Δ = 候補 − 同じ世界のmulti
```

Gはローカルbase fee=0の会計で、成功・revert双方を含む。実支払ETHを終値で評価するため、Pとの照合ができる。取引件数や回転額を利益へ足さない。E_execはAMM手数料・実際の価格影響を含む**約定価格と当時fairの差**であって、純粋な因果的alphaではない。M_carryも「在庫制御を外せば得た利益」の推定ではない。

集計窓は**runStartBlock < inclusion block ≤ finalBlock**。Pの開始境界より前／後の取引を混ぜない。初期資本が共通なのでnoopの初期在庫価格変動を控除できる。Xは専門資産・プロトコルの変化と未復元分を残す残差であり、名称だけで全額を清算利益としない。

確認:
- 全120世界、各3比較対象で[A]と[B]の包含hashの未対応0。[V]の最初と最後の差がP−noopと一致（差0）。再構成観測のblock差分による照合も使用した。
- 現物の量・価格を復元できなかった成功レッグはmulti側にsonnet場71／opus場34。微小額の未復元分をXへ残した。multiの世界別|X|最大はそれぞれ**0.006157／0.002047 USDC未満**、sonnet側は**0.000001未満**。これらを「取引なし」と数えない。
- Xの定義による算術閉合と、[V]による独立の総額照合を区別する。モジュール単独の因果効果をこの恒等式からは識別できない。

## 3. 主因の仮説（最大3つ）

### H1 — 取れる機会と資金量を過度に削っている（特にsonnet）

**測定根拠**: sonnetの回転額12.01%、全域ΔE_execの不足、失敗ゼロでも大差の世界、対応約定での高入札・先行。whaleの2脚終値寄与不足も大きい。

**コード根拠**:
- sonnet `agent.ts:24-42,132-189`: 60bpsを入口だけでなくnetから引き、同じnetで深さサイズとprofit/bidを計算。50 USDC最小サイズ、0.5利益floor、資産8%cap、±20%在庫帯、2block cooldown、最終4block停止が重なる。
- multi `agent.ts:27-33,83-112,145-171`: 2脚優先、残高2.5〜25%、深さcap・在庫帯・cooldownなし。単脚sizeはraw gap依存。参照コードの説明コメントだけで「中立」と見なさず、実際の在庫露出を会計に残す。
- opus `agent.ts:469-501`: 深さの0.15%、財布側90%、net35bpsによる縮小。候補の生成時点で財布を予約してから選抜する（506-559、1189-1193、1227-1229）ため、採用されない候補の予約が後続機会を狭める可能性もある。この部分の損益は未識別。

**既存データだけの検証**: §2で実施済みの回転額・サイズ・同機会順序・単脚/2脚寄与を全レジームで照合。さらに[B,M]のmulti約定blockに対応する候補noopを[A]で数え、[M]のgap/depth/在庫フローを重ねれば、入口に存在した機会の候補集合を限定できる。ただし[M]は後再構成で、完全な入力観測と候補別reject理由がない。**既存ログだけで60bpsと在庫帯の純粋な寄与割合まで確定できない**。

**反証条件**: 候補の見送り時点で実際には資金・安全制約を満たす利益機会がない、または同程度の数量・同一機会に絞っても不足が主に約定後の損失で説明されるなら、「入口/サイズ不足が主因」を下げる。opus spike/41101は、数量不足だけの説明を既に反証している。

### H2 — 在庫を戻す売買が獲得したエッジを消す（特にopus）

**測定根拠**: forcedに確実に対応する2,576成功レッグのE_execは−62,879.61。opusはsonnetほど回転額が小さくないのに、全現物E_execは60世界で38,468.27に留まる。初期在庫へ戻ることと、その復元コストを回収することは別である。

**コード根拠**: opus `agent.ts:606-677` は±15%帯を超えると半帯へ戻し、残18blockでは原点へ戻す。通常の復元もfair比−40bpsまで許容。forcedはprofit=0・slippage150bps・既定feeへ落ちる（710-727）。エントリー70bpsでも、次の復元・価格変動・gasを合わせた往復が正とは限らない。

**既存データだけの検証**: forced部分の上記抽出は実施済み。追加で[A,M]の同base・逆方向フローを時系列に照合し、エントリー→復元の同数量だけを対応させれば、現金損益・保有block数・最後18block内外を分離できる。fifo等の対応規則を先に固定し、bundle由来や清算wrap分を混ぜない。今回その完全なlot照合は未実施。終値寄与−14,752.53を「forcedを消した改善額」とはしない。

**反証条件**: 対応エントリーを含めた往復が実費後で十分に正、あるいは強制復元がより大きい後続損失を回避し、損失往復の寄与がP差の小部分しかないなら主因から下げる。実際、M_carryがmultiより有利であることは、防御が無価値との主張を反証している。

## 4. 修理設計 — 独自の「実費後利益と回収余力で配分する裁定コア」

### 4.1 基盤と独自性

**sonnet由来xb-coreを会計・資金・回収の土台として、新しい一体の意思決定系を設計する。** multi-arbの分岐、サイズ式、定数、参照設定を移植しない。既存lib/SDKを利用した箇所とsonnet/xb由来は明示し、提出用ascon-*に隔離する。現時点では実装しない。

独自性の実質差は、(a)全候補の実費後利益から資金を割り当て、(b)単脚・部分bundle・専門収益の由来を残高差分で区別し、(c)競争状態と事後約定品質が悪化した方向だけを縮小し、(d)期限までの回収可能性を入口へ戻すこと。参照名や定数を変えたことを独自性の根拠にしない。

### 4.2 具体的な組合せ

## 付録B. 再計算手順と保全

新しいrunを起動せず、次の順に読み取れば再現できる。抽出スクリプト・中間ファイルは本worktree／計測worktreeへ保存していない。

1. [Q]の6 indexをTSVとして読み、各60一意キーとexit_code、12×5を検査。`cand`をindex名でsonnet/opusへ対応させる。D0は別集合。
2. summaryの全非baselineのPでμと母σを計算。Tを世界内で求め、regime→全域の順で平均。`netPnlUsdc`は使わない。
3. agent JSONLのsubmittedをhash辞書へ、submit_failed/rejectedは別件数へ。blocks.csvをhashで結合し、採点窓内の成功・revertを分類。
4. 成功現物はnotionalsからq,p,side,baseを取得し、包含blockとfinalBlockのfairでE_exec/M_carryを計算。欠測はXへ残し件数を表示。bundleはbundleIdで分類し、単なるtx数を裁定回数と呼ばない。
5. 全包含gasを実費×終値で評価し、P−noopから残差Xを計算。eventsの再構成alphaValueUsdcの最初/最後も独立照合する。
6. 専門帰属は各blockのΔalpha + gas − 現物終値寄与を計算し、そのblockの専門action集合で分類。複数actionを勝手に一つへ割らず、専門txがないblockの残差も残す。
7. 閾値・サイズ・入札・在庫のコード読取と、既存ログで実測できる結果を分ける。counterfactual利益や未保存の候補却下率を補完しない。
