# Stage2 diagnostic guard prototype

This is a stand-alone, diagnostic-only prototype. It is not wired into the production runtime or runbook. `prepare` records `prepared_blocked_until_parent_review`; both the `run` and direct `invoke` CLI actions are hard-disabled and return exit 78 for syntactically valid required arguments, before authorization or process launch. Malformed arguments are rejected by argparse before execution. The current implementation does not bind world argv/source/prompt/roster/model route into the receipt and has no external watchdog for supervisor SIGKILL/OOM. A lock-free cleanup fallback now persists a fail-closed STOP sentinel before its best-effort registry scan; it still cannot prove cleanup of an unregistered or later-starting process. `supervise` and `invoke` functions remain callable by in-process test harnesses, not an operational or OS security boundary. Do not launch a real world or model with this prototype. It never asserts G3 acceptance.

The plan is a JSON file with `schema: 2`, a unique `job_id`, `diagnostic_only: true`, a plain-integer `max_cli_starts` from 1 through 6, and a required `input_hash_policy` with exactly `version: 1`, `max_file_bytes`, `max_unique_bytes`, and `max_unique_files` as plain integers. There are no inferred policy defaults. Current fixed implementation ceilings are 64 MiB per unique file, 128 MiB combined unique bytes, and 1,024 unique files; every plan must select limits at or below all three ceilings. These are defensive code ceilings, not universal operator settings. They were chosen with headroom over metadata from a historical, unconfirmed candidate state copy (37,115,128 bytes across 249 files; largest file 36,446,357 bytes). That inventory does not establish the copy as a Stage2 input or predict future dump sizes. Plans exceeding a code ceiling require a separately reviewed implementation change.

The plan also pins an absolute CLI executable path and SHA-256, an absolute MCP JSON file containing exactly `{"mcpServers": {}}` plus its SHA-256, `forced_args` exactly matching the policy below, input paths including the exact `prompt.md` and roster, a `model_routing_inputs` object naming those two files, and distinct evidence files for every key in `REQUIRED_PREREQUISITES`. The `frontmatter_model_routing` evidence must record a review of the pinned prompt frontmatter and roster confirming the supported Claude CLI path. The guard pins these input bytes but does not parse the prompt or prove the selected route at runtime; a `codex:*` frontmatter route bypasses the Claude shim and remains an explicit STOP prerequisite. Every evidence reference must have `status: "verified"`, a file under a non-root `evidence_root`, and a matching SHA-256. The guard records the paths and hashes and rejects reused evidence files; it does not inspect whether claims in those files are true. The parent must review their contents. In particular, B05, B07, B08b, and account exclusivity require separate evidence and are never synthesized by this tool. The prerequisite keys also include the current auth JSON schema, extra usage disabled, pinned Node/tsx, CLI option support, and a managed-settings/hooks inventory. Schema-1 plans and receipts are rejected; create new synthetic schema-2 plans rather than inferring missing policy.

The guard appends these restrictions to every pinned CLI invocation:

```json
["--restricted", "--tools", "", "--strict-mcp-config", "--mcp-config", "<pinned empty MCP config>", "--setting-sources", ""]
```

The pinned CLI's own help output must be reviewed and recorded in the `cli_restrictions` evidence before any operational plan can pass preflight. On mini, Claude Code 2.1.278 `--help` listed these options and documented `--tools ""` as disabling all tools. `--restricted` ignores user, project, and local settings and refuses `bypassPermissions`; therefore the shim removes the runtime's `--permission-mode bypassPermissions` pair before adding the restrictions. Managed settings still apply, so their hooks and policy require explicit inventory evidence before any operational plan can pass. If the pinned CLI version differs or does not support these options or their empty-value semantics, keep Stage2 stopped and revise the design. The CLI accepts only the exact `llm.ts` argument shape, requires `-p <prompt>` plus `--model haiku`, and rejects every additional option or alternate spelling. It removes `NODE_OPTIONS` and `G3_*`, refuses inherited API/provider, proxy, and runtime-injection variables, and pins `ERIS_LLM_MODEL=claude-cli:haiku` for the supervised world. It uses the pinned shim for the supported Claude path; this prototype does not provide an OS sandbox against a malicious world process or alternate absolute-path executables.

The functions contain a start ledger, bounded scanning of work files, and process-group cleanup paths, exercised by fake-process tests only. A fake supervisor run cannot report normal completion unless it records a successful guarded CLI exit and observes a nonempty `cand.llm.jsonl` under the watched tree; absence of either publishes STOP. This is only a local coverage floor, not proof that the watched tree matches the real runtime output path or the file came from the expected agent. Log and world stdout files themselves have no size cap, and no child-process or OS resource limit is enforced. A later static review identified log-scan starvation, incomplete backlog accounting, and FIFO/path races. The current candidate walks from an opened directory descriptor with bounded `os.scandir(fd)`, reopens each component with no-follow/nonblocking flags, and checks regular-file type and device/inode before reading. Symlinks, unsafe log entries, inaccessible subdirectories, and tree-limit overruns fail closed. Control JSON, the lock file, and the start ledger use nonblocking regular-file opens; JSON size, ledger size, lock wait, and `ps` calls are bounded. Emergency CLI cleanup attempts to read only registered job-owned process groups if the control lock is unavailable; it retains the ownership record and reports incomplete cleanup. STOP markers use HTTP/status/code context for 429/529, delimited rate/quota phrases, and explicit structured error/fallback fields; a trailing numeric status that has no delimiter triggers after one second of idle or at EOF. An ordinary `error` token, decimal/price number, or alphanumeric-embedded code is not sufficient. These controls do not make this an operational or OS security boundary. Completion record hashes detect accidental mismatch only: the same UID can rewrite start, log, and result evidence. The argv digest is compared with the reserved start record but is not an independent attestation. Remaining reviewed limitations include unbound execution identity, no independent owner if the supervisor dies, a separate-session descendant can escape the owned process group (both world and CLI stdout holders are detected after five seconds but cannot themselves be reaped), same-UID control-file mutation, a pre-registration CLI cleanup window if STOP cannot reacquire the lock, a recorded `ps` process-start token checked before TERM and KILL that narrows but does not eliminate PID/PGID reuse races, log-offset rewrite detection, and unverified correspondence between `ERIS_RUN_DIR` and the runtime's final output path. The CLI memory-file loading behavior (including `CLAUDE.md`) is also unverified; restricted settings-source flags are not evidence that memory injection is disabled. The CLI `run` and `invoke` entrypoints remain hard-disabled. Internal Python functions remain callable by test harnesses and are not a security boundary; G3 remains BLOCKED.

Create each job directory at a fresh path. Preparation is synthetic-review-only and never grants execution approval:

```sh
python3 -I stage2_guard.py prepare --plan /path/to/plan.json --job-dir /path/to/new-job
```

The `run` and `invoke` commands are intentionally hard-disabled and return exit 78, even when given valid-looking receipt data and a fake command. Do not wire `supervise` or `invoke` into another launch path; their process controls are tested with fake processes only.

Use fake CLI and fake process trees for validation. Do not run a real model, simulator, Anvil, or world from this prototype until the parent has reviewed the source, every prerequisite has current evidence, and the runbook has been updated in a separate reviewed change. A prepared receipt is intentionally not a launch approval.

STOP scanning recognizes bounded structured status/code fields and explicit failure phrases such as `status code 429`, `429 Too Many Requests`, and `RateLimitError`; a plain `rate limit` mention does not stop. The recognized patterns do not prove detection of every provider envelope or confirm the actually routed model/provider. Those remain external preflight obligations. This is synthetic pattern coverage, not proof of all provider output formats. The CLI registry is checked with `lstat` and must be an owned real directory; same-UID replacement races remain outside this prototype boundary.

Limits: receipt files use read-only filesystem permissions as an accidental-overwrite control, not a cryptographic or administrator-proof seal. The internal review hash is not an authentication mechanism. Evidence contents, account state, extra-usage status, managed settings/hooks, CLI option semantics, and actual provider billing remain external review obligations. Process descendants that deliberately create a new session cannot be terminated by their parent's group. Runtime files are scanned only under the redirected job work directory and only for `.log`, `.json`, `.jsonl`, and `.txt`; captured world and CLI stdout are also monitored. An entry of any kind that disappears between directory enumeration and `lstat` is skipped for that poll and its cached cursor, tail, and deferred-marker state are discarded; final scanning counts it toward the bounded race policy, while a directory disappearing during later descent fails immediately; file removal or replacement after enumeration discards that path's cursor and is retried. Cursor identity requires filesystem birth time; the supported scanner platform is macOS with Python `stat` birth-time support. On systems where Python does not expose birth time, scanning fails closed as unavailable. Change time is not used because normal appends would invalidate the cursor and could cause a false backlog stop. The scanner also verifies birth identity and single-link status after opening each file; a change between enumeration and open is retried, while a stable hardlink is rejected. Final scanning stops after three observed file-entry disappearance/replacement races or 64 final polls, whichever occurs first. A file-race observation on the third occurrence produces fail-closed STOP (two retries after the initial observation); clean polls that remain pending do not reset that race count. Directory-component disappearance, identity change, or enumeration I/O errors fail closed immediately rather than retrying. Every symlink under the watched work tree is rejected, regardless of its filename suffix or target type. Regular files with unsupported extensions, including extensionless files and rotated suffixes such as .log.1, trigger fail-closed STOP. The real runtime output-path and format inventory remains unverified. Plan-selected inputs and evidence share the explicit byte/file budget; canonical paths and opened file identities are counted once, with bounded reads and before/after descriptor metadata checks. These checks bound ordinary preparation/verification work and detect ordinary concurrent changes, but they are not same-UID hostile-file attestation. Runtime log limits remain separate, and no child-process resource bound is established by this prototype.

Completion protocol: after checking every reserved CLI result and confirming no active CLI record, the gate publishes `completion-fence.json` with `reason: completion_gate_passed` while holding the control lock. A preexisting fence is an error and cannot satisfy the gate. That dedicated fence blocks any later shim reservation and is separate from `stop.json`, which is reserved for abnormal/unsafe conditions. Only after owned-group cleanup returns successfully and no failure STOP exists does the supervisor publish `terminal.json` with `reason: world_exit`; these are still same-UID consistency records, not attestation. STOP is the final authority: a later STOP publication is allowed to remove an earlier terminal marker. When both markers are present after a crash or failed unlink, readers must check `stop.json` before accepting `terminal.json`; coexistence is failure. If terminal rollback and STOP persistence both fail after a terminal link, disk state may contain a fence plus a normal terminal and no STOP even though `supervise` raises. Therefore disk markers alone are insufficient: an acceptance reader must call `verify_job_outcome(job, supervisor_returncode)` with the independently observed supervisor process status; the helper requires exact integer 0, no STOP before or after reading, a valid fence and normal terminal, a nonempty no-follow direct child `work/cand.llm.jsonl` (nested files with the same basename do not count); this candidate must be regular and have one hard link, as must scanned logs. A replacement or link-count change between enumeration and open is retried and rechecked. Complete hash-checked CLI results for every start within the receipt cap, and a completely empty active registry. A terminal without independently observed supervisor exit 0 is never acceptance. The reader also verifies the parent review token against the receipt; it is not wired into the currently disabled runtime CLI. The helper reads are not atomic with concurrent writers; its final STOP check narrows but cannot eliminate a later same-UID write. `supervise()` returns the world status, not its own process wait status, so only an external parent that observes the supervisor process may supply this argument. This remains same-UID consistency checking, not attestation; the helper caller must not derive the process status from these files. Directory `fsync` provides process-crash ordering only, not a claim of hardware power-loss durability. An exception before the gate records `supervisor_error` when no other STOP exists; a cleanup failure after the gate leaves the completion fence plus a failure STOP, without terminal success. Neither record proves the runtime used the watched path or that every model call passed through the shim.
